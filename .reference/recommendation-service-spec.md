## 0. 공통 규칙

- **인증**: 게이트웨이가 JWT 에서 주입한 `X-User-Id`(UUID)로 호출 주체를 식별. 헤더 없으면 401.
- **식별자**: 사람은 전부 `userId`(UUID). 반경검색 인덱스도 userId 축으로 통일돼 있다.
- **응답 래퍼**: 공통 `ApiResponse<T> { success, message, data }`.
- **에러 매핑**: 검증 실패 400 · 미인증 401 · 권한 없음 403 · 리소스 없음 404.
- **소유 테이블 없음**: 이 서비스는 DB 를 갖지 않는다. 입력은 Redis(다른 서비스가 채운 캐시)와 Kafka 뿐이다.

## F2-1. 추천 후보 서빙

- **목적**: 스와이프할 상대 카드를 가까운 순·취향 순으로 내려준다.
- **요청**: `X-User-Id` + 선택 `cursor`, `size`
- **응답**: `200 OK`
  ```json
  { "success": true, "data": {
      "items": [
        { "profile": { "userId": "...", "profileId": "...", "age": 28, "gender": "FEMALE",
                       "bio": "...", "tags": ["러닝","여행","커피"], "imageUrl": null },
          "distanceKm": 3.0, "sharedTags": ["러닝","여행"] }
      ],
      "nextCursor": "Mjc3NjYwNWM6MQ" }}
  ```
- **비즈니스 규칙**:
  1. **반경**: 내 `prefDistanceKm` 안의 사람만. 미설정이면 기본값(30km), 상한(200km)으로 자른다.
  2. **성별**: 내 `prefGender` 와 상대 `gender` 가 일치해야 한다. 미설정이면 무관.
  3. **나이**: 내 `prefAgeMin~prefAgeMax` 안이어야 한다. 미설정이면 무관.
     **선호가 설정됐는데 상대 카드에 그 값이 없으면 제외**한다(확인 못 한 후보를 조건에 맞는 척 보여주지 않는다).
  4. **본인 제외** · **이미 본 사람 제외**(F2-3).
  5. **카드 없는 사람 제외**: 프로필을 안 쓴 사람은 보여줄 내용도 거를 근거도 없다.
  6. **정렬**: 거리와 관심사 겹침을 함께 본 점수 순. **가까운 순이 아니다** —
     멀어도 취향이 겹치면 위로 올라온다.
  7. **`sharedTags`**: 나와 겹치는 관심사를 함께 내려 "관심사 2개 일치" 같은 추천 이유를 표시할 수 있게 한다.
- **페이지네이션**:
  - `cursor` 없이 호출 = **새로고침**(후보를 다시 계산한다).
  - `cursor` 를 주면 그 계산 결과 안에서 이어 읽는다 → **같은 사람이 두 번 나오거나 건너뛰어지지 않는다.**
  - `nextCursor` 가 `null` 이면 끝.
  - **깨졌거나 만료된 커서는 에러가 아니라 첫 페이지**로 처리한다(400 으로 튕기지 않는다).
  - `size` 기본 10, 상한 50.
- **엣지**:
  - 위치를 한 번도 올리지 않은 유저 → **빈 피드(200)**. 반경검색의 기준점이 없기 때문이며 에러가 아니다.
  - 반경 안에 아무도 없음 / 전원 seen → 빈 피드.
- **에러**: 401(헤더 없음).
- **완료 기준**: 반경·성별·나이·본 사람 제외가 반영된 피드가 커서로 끊김 없이 내려온다.

## F2-3. seen 기록

- **목적**: 이미 판단을 끝낸 상대를 다음 피드에서 뺀다.
- **기록 시점 2가지**:
  1. **좋아요/패스**(자동) — `like-relay` 이벤트를 구독해 적재. 클라이언트가 따로 호출하지 않아도 성립한다.
     LIKE/PASS/SUPER 를 구분하지 않는다(어느 쪽이든 "판단이 끝난 사람").
  2. **카드 노출**(명시) — `POST /api/feed/seen { "userIds": [...] }`. 보고 넘긴 카드를 클라이언트가 알려준다.
- **규칙**:
  1. **멱등**: 같은 상대를 여러 번 넣어도 안전.
  2. 자기 자신은 무시.
  3. 빈 배열은 400.
  4. 기록은 90일 보관하며, 활동하면 만료가 갱신된다.
- **파생 효과**: 매칭은 서로 좋아요를 눌러야 성립하므로 **매칭된 상대는 반드시 내 seen 에 있다**
  → "이미 매칭된 상대 제외"에 별도 조회가 필요 없다.
- **완료 기준**: 좋아요/패스한 사람은 다음 피드에 다시 뜨지 않는다.

## 주요 예외/엣지 케이스

| 상황 | 기대 동작 |
|---|---|
| 위치 미등록 유저 | 빈 피드(200) — 에러 아님 |
| 선호 미설정 유저 | 기본 반경·필터 없음으로 피드 제공(빈 피드가 아니라) |
| 선호 캐시 만료 | 위와 같음(제약 없음으로 fallback) |
| 커서 위조/깨짐 | 첫 페이지부터 다시 |
| 스냅샷 TTL 만료 후 옛 커서 | 버전 불일치 감지 → 재계산 후 첫 페이지 |
| 상대가 프로필 삭제 | 서빙 시점에 카드가 없으면 그 자리만 빠진다 |
| 페이지가 필터로 전부 비었을 때 | 다음 구간까지 훑어서 채운다(빈 배열 + 커서로 끝난 것처럼 보이지 않게) |
| 반경 안 전원 seen | 빈 피드 |
| 헤더 누락 | 401 |
| `userIds: []` | 400 |

## 완료 기준 (기능 인수 시나리오)

1. A 주변에 조건에 맞는 B·C 가 있으면 피드에 뜬다. 조건에 안 맞는 D(성별)·E(나이)는 안 뜬다.
2. B 가 C 보다 멀어도 관심사가 겹치면 위에 온다.
3. `size=1` 로 끊어 읽어도 B → C 순서가 유지되고 마지막에 `nextCursor: null`.
4. A 가 B 에게 좋아요를 누르면 다음 피드에서 B 가 사라진다.

## 결정 사항
- [x] **식별자 축 통일** — `geo:users` 멤버를 profileId → userId 로 전환. 추천에서만 필요한 매핑 조회를 없앴다. ✅
- [x] **선호값은 별도 캐시** `profile:pref:{userId}` — 카드에 섞으면 남의 선호가 함께 노출된다. ✅
- [x] **SINTERCARD 미사용** — 카드를 이미 MGET 하므로 태그 겹침은 메모리에서 계산한다. ✅
- [x] **seen 은 이벤트로 채운다** — matching 이 남의 서비스 키를 직접 쓰지 않게. ✅
- [x] **커서 = 스냅샷 버전 + offset** — 재계산으로 순서가 흔들려 생기는 중복/누락을 막는다. ✅

### 남은 선택 항목
- [ ] 활동성(최근 접속) 을 랭킹에 반영 — 지금은 거리·태그만 본다
- [ ] 차단(block) 목록 제외 — 차단 기능 자체가 아직 없다
- [ ] 스냅샷 사전 계산(위치/선호 변경 시 미리 갱신) — 지금은 요청 시 계산
- [ ] seen 을 Bloom filter 로 — SET 이 아주 커지면
