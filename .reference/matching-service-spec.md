>

---

## 0. 공통 규칙

- **인증**: 모든 API는 게이트웨이가 JWT에서 주입한 `X-User-Id`(UUID)로 호출 주체를 식별. 헤더 없으면 401.
- **식별자**: 사람은 전부 `userId`(UUID). (프로필 단위 아님)
- **응답 래퍼**: 공통 `Response<T> { status, message, data }`.
- **에러 매핑**(전역 예외 핸들러 전제 — 미구현 시 임시 500): 검증 실패 400 · 미인증 401 · 권한 없음 403 · 리소스 없음 404.
- **좋아요 종류**: `LIKE`(좋아요) · `PASS`(패스/거절) · `SUPER`(슈퍼좋아요). 매칭 판정은 `LIKE`/`SUPER`만, `PASS`는 저장만.
- **매칭 상태**: `ACTIVE`(유효) · `UNMATCHED`(해제).

## F-M1. 좋아요/패스 접수

- **목적**: 사용자가 상대에게 LIKE/PASS/SUPER를 표현한다. 판정은 비동기이므로 **즉시 202로 응답**(사용자는 기다리지 않음).
- **액터/트리거**: 로그인 사용자가 카드에서 스와이프/버튼.
- **요청**: `X-User-Id`(=fromUserId) + body `{ "toUserId": UUID, "type": "LIKE"|"PASS"|"SUPER" }`
- **응답**: `202 Accepted` (판정 결과는 담지 않음 — 성사 여부는 F-M3 알림 / F-M4 목록으로 확인)
- **비즈니스 규칙**:
  1. **자기 자신 금지**: `fromUserId == toUserId` → 400.
  2. **중복 접수 멱등**: 같은 상대에게 또 눌러도 안전(내부 PK 흡수). 같은 type 재전송은 사실상 no-op.
  3. **type 변경 허용**: 같은 상대에게 다른 type 재접수 시 최신 값으로 갱신(예: PASS→LIKE 마음 변경 가능). LIKE로 갱신되면 판정 대상이 된다.
  4. **PASS**: 저장만, 매칭 판정 제외.
  5. **이미 매칭된 상대**: 재접수해도 재매칭 안 됨(내부 UNIQUE로 no-op).
- **검증**: `toUserId` UUID 형식 · `type` 3종 enum · 헤더 UUID.
- **에러**: 400(자기자신/형식), 401(토큰 없음).
- **비고**: `toUserId` **실존 유저 검증은 선택**(안 하면 유령 like가 저장될 뿐 매칭 안 됨). 데모는 skip 가능.
- **완료 기준**: 유효 요청 시 **202 즉시** 반환 + 내부적으로 판정 큐에 적재됨.

## F-M2. 매칭 판정 (내부, 비동기)

- **목적**: 접수된 좋아요를 **직렬 처리**해 상호 호감이면 매칭을 성사시킨다.
- **트리거**: F-M1이 적재한 이벤트(쌍 단위로 직렬).
- **처리 규칙**:
  1. 좋아요 저장(멱등).
  2. `type ∈ {LIKE, SUPER}`일 때만 **역방향 확인**: 상대가 이미 나에게 LIKE/SUPER 했는가?
  3. 역방향 존재 → **매칭 성사**: 매칭 1건 생성(항상 두 유저 정렬 저장) + 후속 이벤트 발행을 **원자적으로**.
  4. `PASS` → 저장만, 판정 제외.
- **동시성/정합성**:
  - **엇갈림 방지**: A→B, B→A가 같은 처리 단위로 직렬화되어 "둘 다 매칭 못 만듦/둘 다 만듦" 같은 레이스 없음.
  - **중복 매칭 0**: 동일 쌍 매칭은 UNIQUE로 원천 차단.
  - **멱등**: 같은 좋아요가 재처리돼도 결과 동일(매칭 중복 생성 안 됨).
- **완료 기준**: 상호 LIKE/SUPER → **매칭 정확히 1건** + 성사 이벤트 발행. 한쪽만 LIKE면 매칭 없음(대기).

## F-M3. 매칭 성사 후속 — 채팅방 자동 생성 + 실시간 알림 (Saga)

- **목적**: 매칭이 성사되면 **두 사람 전용 DIRECT 채팅방이 자동 생성**되고, **양쪽에 "매칭 성사" 실시간 알림**(채팅방 id 포함)이 간다.
- **기능 관점 흐름**: 매칭 성사 → 채팅방 1개 생성 → (준비 완료 후) 양쪽 알림.
- **규칙**:
  1. **채팅방은 매칭당 정확히 1개** (재수신/재처리에도 중복 생성 안 됨).
  2. **알림 시점**: 채팅방 id가 확정된 **뒤에** 발사 → 알림에 `channelId` 포함(클라가 바로 방 오픈 가능).
  3. **온라인**: 실시간 push. **오프라인**: 실시간 push는 못 받아도 **F-M4 목록에서 매칭 확인 가능**(알림 유실이 매칭 유실이 아님).
  4. 전 구간 **멱등**(채팅방 중복 생성/중복 백필/중복 push 무시).
- **완료 기준**: A↔B 매칭 → 채팅방 **1개**, 양쪽 알림(온라인 시), F-M4에 `channelId`와 함께 노출.

## F-M4. 매칭 목록 조회

- **목적**: 내 유효한 매칭들을 상대 프로필 카드 + 채팅방과 함께 본다.
- **요청**: `X-User-Id` (+ 선택 커서/size)
- **응답**: 공통 래퍼 안에 매칭 배열
  ```json
  { "success": true, "data": [
      { "matchId": "019fd5fe-bcf2-744c-9fb1-bd1ce61ce02f", "channelId": 2,
        "partner": { "userId": "...", "profileId": "...", "age": 26, "gender": "FEMALE",
                     "bio": "...", "tags": ["러닝","여행"], "imageUrl": "대표사진 or null" },
        "matchedAt": "2026-08-06T16:34:29.383865" }
  ]}
  ```
  > 카드 캐시 미스면 `partner` 에 `userId` 만 채워져 나온다(나머지 null / tags []).
- **비즈니스 규칙**:
  1. `status = ACTIVE`만.
  2. **상대** = 매칭의 두 유저 중 내가 아닌 쪽.
  3. **상대 프로필 카드** 포함 → **Redis 카드 캐시 `profile:card:{userId}`**(JSON: profileId·age·gender·bio·tags·대표 imageUrl)에서 배치 조회(MGET). 이 캐시는 **profile-service가 프로필 생성/수정(및 활성 프로필 전환) 시 채운다.** 캐시 미스 시 fallback: profile-service REST 조회 또는 최소 정보(userId)만.
  4. `channelId`가 아직 준비 안 됐으면(성사 직후 짧은 순간) `null` 가능 → 클라는 "준비 중" 처리.
  5. **정렬**: 최신 매칭 순.
- **에러**: 401.
- **완료 기준**: 내 ACTIVE 매칭이 상대 카드 + channelId와 함께 최신순으로 반환.
- **열린 항목**: 페이지네이션(커서) 필요 여부 — 매칭 수가 많지 않으면 단순 목록도 가능.

## F-M5. 언매치

- **목적**: 매칭을 해제한다.
- **요청**: `X-User-Id` + path `matchId`
- **응답**: `200 OK`
- **비즈니스 규칙**:
  1. **권한**: 그 매칭의 당사자(두 유저 중 하나)만 가능 → 아니면 403.
  2. `ACTIVE` → `UNMATCHED`로 전환. 목록(F-M4)에서 사라짐.
  3. **멱등**: 이미 UNMATCHED면 no-op(200).
  4. **채널 CLOSED**(확정): 언매치 시 그 DIRECT 채널을 **CLOSED로 닫는다.** 채널은 message-service 소유이므로 matching이 직접 못 고침 → **언매치 이벤트를 발행** → message-service가 `channel.status=CLOSED` 처리. CLOSED 채널은 **신규 메시지 전송 거부**(message-service 가드).
  5. **재매칭 정책**(열린 항목): 언매치 후 좋아요 기록이 남아 재판정 시 다시 매칭될 수 있음 — 막을지 결정 필요.
- **에러**: 403(당사자 아님), 404(없는 matchId), 401.
- **완료 기준**: status UNMATCHED, F-M4에서 제외.

---

## F-M6. 받은 좋아요 조회 (선택)

- **목적**: 나를 좋아한(LIKE/SUPER) 사람 목록.
- **요청**: `X-User-Id`
- **응답**: 상대 프로필 카드 배열.
- **규칙**:
  1. `to_user_id = 나` AND `type ∈ {LIKE, SUPER}`.
  2. **이미 매칭된 상대는 제외**(이미 F-M4에 있으므로).
  3. PASS는 제외.
- **완료 기준**: 나를 좋아한(아직 매칭 전) 사람들이 카드로 반환.

---

## 상태 전이

```
like.type :  (없음) ──접수──▶ LIKE / PASS / SUPER  (재접수 시 갱신)
match     :  (없음) ──상호 LIKE/SUPER──▶ ACTIVE ──언매치──▶ UNMATCHED
channel   :  매칭 성사 ──Saga──▶ DIRECT 채널 1개 (matchId에 귀속)
```

## 비기능 요구 (품질)
- **응답성**: 좋아요 접수는 판정을 기다리지 않고 **즉시 202**.
- **정합성**: 동시 스와이프 폭주에도 **매칭 중복 0 / 유실 0**.
- **복원력**: 판정/서버가 중간에 죽어도 재기동 후 결국 매칭·알림 도달(멱등·재처리).

## 주요 예외/엣지 케이스
| 상황 | 기대 동작 |
|---|---|
| 자기 자신에게 좋아요 | 400 |
| 같은 상대 같은 type 반복 | 멱등, 상태 불변 |
| PASS 후 LIKE | type 갱신, 판정 대상 됨 |
| A→B, B→A 동시 좋아요 | 매칭 정확히 1건(엇갈림/중복 없음) |
| 이미 매칭된 상대에게 또 좋아요 | no-op(재매칭 안 됨) |
| 존재하지 않는 toUserId | (검증 skip 시) 저장되나 매칭 안 됨 |
| 남의 매칭 언매치 시도 | 403 |
| 없는 matchId 언매치 | 404 |
| 매칭 직후 목록 조회(백필 전) | channelId=null 가능("준비 중") |
| 수신자 오프라인 | 실시간 알림 못 받아도 F-M4 목록엔 존재 |

## 완료 기준 (기능 인수 시나리오)
1. A가 B에게 LIKE → 202. B 목록엔 아직 매칭 없음.
2. B가 A에게 LIKE → 202. → 매칭 1건 생성, 양쪽 F-M4에 상대 카드+channelId 노출, (온라인 시) 실시간 알림 수신.
3. 같은 쌍 반복/동시 스와이프 → 매칭 여전히 1건.
4. A가 언매치 → 양쪽 F-M4에서 사라짐(재요청 멱등).

## 결정 사항
- [x] F-M4 상대 프로필 카드 → **Redis 캐시 `profile:card:{userId}`** (profile-service가 채움, matching이 MGET) ✅
- [x] F-M5 언매치 시 채널 → **CLOSED** (언매치 이벤트 → message-service가 닫음 + 전송 차단) ✅
- [x] 언매치 후 **재매칭 안 함** — 판정이 쌍의 매칭 존재만 보고 끊으므로 UNMATCHED 쌍은 다시 매칭되지 않는다.
      같은 이유로 F-M6 도 "매칭 이력이 있는 상대"를 상태 무관하게 제외한다(눌러도 아무 일 없는 카드를 안 보여줌).
- [x] **에러 매핑 구현 완료** — `GlobalExceptionHandler` 로 400/401/403/404. (헤더 누락은 Spring 기본 400 이 아니라 **401**)
