2. StoredImage — 로컬 vs 운영

헷갈리는 핵심을 먼저 짚으면: StoredImage의 필드(모양)는 두 경우가 완전히 같아요. 레코드 구조는 안 바뀌어요. 바뀌는 건 objectKey·imageUrl의 "값"과 그걸 만드는 방식뿐이에요. 그래서 서비스/엔티티는 어느 스토리지든 신경 안 써도 되는 거고요.

같은 파일 내사진.jpg(image/jpeg, 2.3MB)를 올렸다고 할 때:

┌──────────────────┬────────────────────────────────────────────────┬─────────────────────────────────────────────────────────────┐
│       필드       │        로컬 (LocalProfileImageStorage)         │                    운영 (S3/MinIO 구현)                     │
├──────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ originalFileName │ 내사진.jpg                                     │ 내사진.jpg ← 같음                                           │
├──────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ storedFileName   │ 018f...uuidv7.jpg                              │ 018f...uuidv7.jpg ← 같음                                    │
├──────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ objectKey        │ profile/018f...jpg                             │ profile/018f...jpg ← 문자열은 같은데 의미가 다름            │
├──────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ imageUrl         │ http://localhost:8085/files/profile/018f...jpg │ https://cdn.myapp.com/profile/018f...jpg ← 여기가 진짜 다름 │
├──────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ contentType      │ image/jpeg                                     │ image/jpeg ← 같음                                           │
├──────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ fileSize         │ 2411520                                        │ 2411520 ← 같음                                              │
├──────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────┤
│ 실제 파일 위치   │ {base-dir}/profile/018f...jpg (로컬 디스크)    │ S3 버킷 my-bucket의 키 profile/018f...jpg                   │
└──────────────────┴────────────────────────────────────────────────┴─────────────────────────────────────────────────────────────┘

두 필드의 역할 차이 (왜 둘 다 저장하나)

- objectKey = 스토리지 내부 식별자. "이 스토리지 시스템 안에서 객체가 어디 있나."
  - 로컬: base-dir 기준 상대 경로
  - S3: 버킷 안 오브젝트 키
  - → 삭제·URL 재생성 할 때 이걸로 접근. 스토리지 관리용 핸들.
- imageUrl = 클라이언트가 이미지를 여는 공개 URL.
  - 로컬: 우리 앱이 /files/**로 서빙 → localhost:8085/...
  - S3: CDN/S3가 서빙 → cdn.myapp.com/...
  - → 이게 서빙 주체가 달라서 진짜로 값이 바뀌는 필드.

그림으로

        같은 StoredImage 구조
        ┌─────────────────────────────────────────┐
업로드 →│ originalFileName / storedFileName /       │
        │ contentType / fileSize   ← 값도 동일       │
        │                                           │
        │ objectKey   ← "스토리지 안 위치" (관리용)   │  로컬: base-dir 상대경로
        │ imageUrl    ← "공개 접근 URL" (클라용)      │  S3:   CDN/버킷 URL
        └─────────────────────────────────────────┘
             ↑ 로컬이든 S3든 서비스는 이거 하나만 받으면 됨

정리

- normalize() = 경로에서 ./.. 정리하는 순수 문자열 연산 (디스크 안 건드림).
- StoredImage는 모양 동일, 값만 다름. 특히:
  - objectKey = 스토리지 내부 핸들(삭제/관리용) — 문자열은 비슷해도 "로컬 경로 vs S3 키"
  - imageUrl = 공개 URL(서빙 주체가 달라 값이 진짜 바뀜)
- 그래서 로컬↔S3 교체 시 LocalProfileImageStorage만 갈아끼우면, StoredImage를 받는 서비스·엔티티·DB는 손 안 대도 돼요.
